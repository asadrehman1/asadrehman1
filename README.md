Tech Stack (High Level)

On the frontend, the application is built with Next.js, which gives us server-side rendering and faster page loads.

For data, we communicate with DES (Digital Enrollment Service), which is the backend responsible for storing application details, payment plans, bank information, legal protection status, and everything related to enrollment.



For authentication, we use Auth0 on the server to securely obtain a machine-to-machine token before making requests to DES.



For bank account linking, we use Plaid, so customers can securely connect their bank instead of entering account details manually.



The final agreement is handled through an internal signing SDK, where customers review and electronically sign their enrollment documents.



Throughout the journey, we also use Datadog, FullStory, and GTM for monitoring, analytics, and debugging.



Overall User Journey

Before entering this application, the customer has already completed the earlier steps like application, qualification, and identity verification.

When they arrive here, they'll see a 4-step enrollment checklist:





Confirm Payment Plan



Link Bank Account



Legal Protection



Review & Sign

The customer completes these steps one by one.

Each step opens a modal, the customer provides the required information, and it's immediately saved to DES.

There are also a few informational pages, like Why Enroll and Program Details, which help customers understand the benefits of the program, but they aren't required to complete enrollment.



Questions they might ask

Q1: Why is this a separate application instead of part of the main website?

Answer:
The customer has already qualified before reaching this point. This application focuses only on enrollment, so it's kept separate to make the experience simpler and easier to maintain.



Q2: Does this application store customer data?

Answer:
No. The frontend mainly displays data and sends updates. DES is the source of truth where all enrollment information is stored.



Q3: Why use Next.js?

Answer:
We use Next.js mainly for server-side rendering, better performance, secure server-side API communication, and an improved user experience.



Q4: Why use Plaid instead of manual bank entry?

Answer:
Plaid provides a more secure and reliable way for customers to link their bank accounts while reducing manual entry errors.



Q5: Is the enrollment saved only at the end?

Answer:
No. Each step saves its data to DES as soon as the customer completes it, so progress isn't lost if they leave and come back later.



Q6: Where does Auth0 fit in?

Answer:
Auth0 is only used on the server to securely authenticate our backend requests to DES. Customers never interact with it directly.



We use Auth0 for secure server-to-server authentication. It allows our Next.js server to securely access DES APIs without exposing any credentials to the browser.





If someone asks: "Why are we using Auth0?"





"We use Auth0 so our Next.js server can securely communicate with DES. Since customers don't log in at this stage, we can't authenticate as a user. Instead, our server authenticates itself using Machine-to-Machine (M2M) authentication, gets an access token from Auth0, and uses that token to securely call DES APIs."



If they ask: "What is M2M?"





"M2M stands for Machine-to-Machine authentication. Instead of a user logging in, one server authenticates itself to another service. In our case, our Next.js server authenticates with Auth0, gets an access token, and uses it to communicate securely with DES."



If they ask: "Why can't the frontend call DES directly?"





"Because DES is a protected API. The credentials used to access it must stay on the server. If we exposed them in the browser, anyone could misuse them. That's why all secure communication happens through our Next.js server."



If they ask: "Does Auth0 store customer information?"





"No. In this flow, Auth0 is only used to authenticate our application. It's not used for customer login or storing customer data."



Q7: What happens after all four steps are completed?

Answer:
The customer has completed digital enrollment, their documents are signed, and the enrollment is successfully recorded in DES.





🚀 Step 2 — Enrollment Walkthrough Modal

What is this popup?

Right after someone starts their application, this popup appears automatically. It's basically the app introducing itself: "here's your numbers, here's how the program works, here's what to know before you commit." It has 3 tabs at the top: Quote, How it works, Details. You move between them by clicking "Next" at the bottom, or by clicking directly on a tab name at the top.



Every tab has the same layout: a close button (X) and a chat button up top, the content in the middle, and a button at the bottom to move forward.



One behavior worth knowing: the first time someone goes through, the bottom button just says "Next" and moves them tab by tab. But once they've already seen all 3 tabs once, that same button changes to say "Continue Enrollment" — so next time they open this popup (they can reopen it anytime from a checklist on the main page), they don't have to click through 3 tabs again, they can just jump straight back into their application.


Tab 1 — Quote

This tab shows the person how much they owe and compares two paths: paying their creditors directly vs. going on our program.





At the top, there's a box showing their total eligible debt amount and how many creditors it's spread across.





If someone clicks that box → a "Your Creditors" screen pops up. What to tell them if asked "what's this creditors list?": "This shows the exact list of debts/accounts we've pulled in and included in your plan — basically proof of what we're settling for you." It also has a small expandable section for "don't see all your creditors?" which explains that some accounts might not qualify, and gives a phone number to call if they want to add or remove one.





Total Eligible Debt (the big red number in the box) = add up the currentBalance of every single creditor/debt in the customer's list. If they have 3 creditors owing $4,000 / $5,200 / $3,250 → the box shows $12,450.





Below that box, there's a comparison table — one side shows what they're currently paying their creditors (monthly payment, how many years it'd take, total amount paid), and the other side shows what it looks like on our plan. The idea is to visually show "you pay less per month, finish faster, and pay less overall" on our side.





Bottom line: all numbers shown on the Quote tab are dynamic and based on that specific customer's application data. Nothing is hardcoded or shared across users. The values are generated using the customer's actual debt and creditor information returned from the backend.





The only time we might see incorrect values like $0 or unexpected defaults is when the test application itself doesn't have complete debt data available — which was the case with the temporary/test application ID we used earlier.



Q1: Where does the debt amount and creditor count come from?





It's not a hardcoded value. The amount is calculated dynamically using the customer's actual creditor/debt information returned from the backend when the application is created. We use that data to calculate and display the customer's total eligible debt amount.



"This page helps customers understand the financial impact of joining the program. At the top, we show their total eligible debt and creditor count. Clicking that opens the detailed creditor list. Below that, we compare their current repayment path against the debt relief program so they can understand the potential difference in monthly payment, timeline, and total amount paid."

Q8: How is the comparison table generated?

Answer:



"The comparison data comes from the customer's enrollment information. We show two scenarios: their current payment path with creditors versus the estimated program path."

↓

Important:



If the signing succeeds but our final enrollment submission fails, we do not make the customer sign again. The agreement is already signed through the SDK, so we keep the modal open and show a clear "Submission failed" message with a retry option. The retry only runs our submission API again, not the signing process. If we get a 401 or 403 error, we show a blocking "Session expired" dialog with a single Reload button. There is no login screen or re-authentication because customers are not logged in during enrollment. This error means our server-to-DES authorization failed, not that the customer's session expired. Reloading the page re-runs the server flow, gets a fresh backend token, and reloads the application data while keeping the customer on the same step using the lastTouchpoint URL parameter. For other errors, we don't show this dialog — we use the normal retry flow instead.



short case:
